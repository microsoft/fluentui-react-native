# v0 component maintenance

Use this recipe for components built on `@uifabricshared/foundation-compose`. Confirm the generation with the
[classification guide](classification.md) first; v0 and v1 can live in the same package.

- **R-V0-001:** v0 is maintenance-only. Do not create a v0 component unless the task explicitly requires v0
  compatibility, and do not migrate v0 code to v1, framework-base, or agentic patterns as part of maintenance.
- **R-V0-002:** Preserve settings layering (`mergeSettings`, the settings-name entry, `_overrides`, and
  `_precedence`), slot prop filters, token key lists, and the split between preparation and rendering. Each
  participates in compatibility, composition, or caching.
- **R-V0-003:** Preserve existing `componentRef` APIs. Do not introduce `forwardRef` or a new public `ref`
  convention without an explicit migration requirement.

## Recognize v0 code

v0 code imports from `@uifabricshared/foundation-compose`, `foundation-composable`, `foundation-settings`, or
`foundation-tokens`, and typically has:

- a descriptor such as `IButtonType` with `props`, `tokens`, `slotProps`, optional `state`, and optional `statics`;
- `compose<IButtonType>({...})`, `IUseComposeStyling<IButtonType>`, `ISlots<...>`, and `mergeSettings(...)`;
- settings shaped as `{ tokens, root, ...slots, _overrides, _precedence }`;
- an old unsuffixed export beside a newer `V1` export.

A `deprecated/` or `legacy/` directory is only a hint: native-core's legacy Callout lives under `legacy/` but uses
modern helpers. Representative v0 implementations are
[deprecated Button](../../../packages/components/Button/src/deprecated/Button.tsx),
[deprecated Checkbox](../../../packages/components/Checkbox/src/deprecated/Checkbox.tsx),
[legacy Link](../../../packages/components/Link/src/legacy/Link.tsx),
[Persona](../../../packages/components/Persona/src/Persona.tsx), and
[Stack](../../../packages/components/Stack/src/Stack.tsx).

## Framework model and public API

`compose` combines the lower-level composable, themed-settings, settings, and token systems. Its phases are:

1. resolve and cache layered `settings`;
2. resolve token props into cached slot props and styles through `styles`;
3. run `usePrepareProps` for hooks, state, refs, and instance-specific props;
4. call the hook-free `render` function with prepared `Slots`.

The package publicly exports `compose`, `initializeStyling`, and the compose option, return, settings, styling, and
type-extraction types listed in its `src/index.ts`. The returned component exposes `__composable`,
`.compose(options)`, and `.customize(...settings)`. Prefer the strongly typed component methods:

- `.compose(...)` replaces or augments behavior, slots, styles, settings, or render without adding a React wrapper.
  Settings are appended to the base settings. See
  [PrimaryButton](../../../packages/components/Button/src/deprecated/PrimaryButton/PrimaryButton.ts).
- `.customize(...)` only appends old-style settings entries. Its input retains `tokens`, `_overrides`, `_precedence`,
  and slot-prop keys; it is not the v1 flat token customization format.
- `statics` attaches subcomponents, as in `Stack.Item`.

The exported two-argument `compose(options, base)` form is the underlying API; use `Base.compose(options)` when the
base is already a typed composed component. `initializeStyling` is infrastructure that `compose` installs
automatically, not something component authors normally call.

## Component shape

Define a shared descriptor type and keep slot names aligned:

```ts
interface IExampleType {
  props: IExampleProps;
  tokens: IExampleTokens;
  slotProps: IExampleSlotProps; // must contain root
  state: IExampleState;
}

export const Example = compose<IExampleType>({
  displayName: exampleName,
  settings,
  usePrepareProps,
  render,
  slots: { root: View, content: Text },
  styles: { root: [backgroundColorTokens], content: [textTokens] },
});
```

Typical files are `<Component>.types.ts`, `<Component>.settings.ts`, `<Component>.tokens*.ts`, `<Component>.tsx`,
`index.ts`, and colocated Jest tests and snapshots. Preserve existing public `I`-prefixed types, deprecated exports,
display names, prop names, and v0/v1 aliases.

For a one-slot component, `compose` supplies default preparation and rendering: it applies styling and user props to
`root`. See [deprecated Text](../../../packages/components/Text/src/deprecated/Text.tsx) and
[StackItem](../../../packages/components/Stack/src/StackItem/StackItem.tsx). Multiple slots require an explicit
`render`. Once custom `usePrepareProps` is supplied, it must put the public and native props on the appropriate slot;
the framework does not do that automatically.

## Slots and rendering

- `slotProps` is a named props collection with a required `root`.
- Define each slot as a component or string, or as `{ slotType, filter }`. Use existing filters such as
  `filterViewProps`, `filterTextProps`, and `filterImageProps` so component-only and token props do not reach native
  views.
- Merge prepared props with styling, normally `mergeSettings(useStyling(userProps, lookup), { root: rootProps, ... })`.
  Later entries win, including merged styles and class names.
- Render prepared slots as `<Slots.root>` and `<Slots.content>`. Their prepared props are already captured; pass only
  additional render-time props in JSX.
- Children are removed before preparation and supplied to `render` as `...children`. Decide explicitly where they
  belong, as Button, Link, and Stack do. Conditional slot rendering is safe because all hooks already ran.
- Put `/** @jsxImportSource @fluentui-react-native/framework-base */` first in files that render callable `Slots` with
  JSX. This pragma supports the legacy slot runtime; it does not make the component a framework-base pattern.

## Settings, tokens, and styling

- Type settings as `IComposeSettings<IExampleType>`. Entries are layered in array order and may be a settings object, a
  theme settings name string, or a `(theme) => settings` function. Keep objects and functions stable and never mutate
  cached settings.
- Use `_precedence` to define state application order and `_overrides` for state-specific settings; nested overrides
  are supported. Settings names such as `buttonName` load theme-provided component settings.
- `useStyling(props)` uses props as the default override mask. For derived interaction state, pass an override lookup
  function or mask, as in legacy Button, Checkbox, and Link.
- Declare token-to-slot processing in `styles`. Reuse operation sets such as `backgroundColorTokens`, `borderTokens`,
  `foregroundColorTokens`, and `textTokens`; use `{ source, target, lookup }` for mappings and theme lookup.
- For component-specific calculations, use `styleFunction` and list every token key that affects the result. See
  [Persona root tokens](../../../packages/components/Persona/src/Persona.tokens.root.ts),
  [Persona text tokens](../../../packages/components/Persona/src/Persona.tokens.texts.ts), and
  [Stack tokens](../../../packages/components/Stack/src/Stack.tokens.ts). Accurate key lists are required for
  memoization.
- When a slot is itself composed and supports a token, token processing can forward that token to the child instead of
  producing a parent-owned style. Preserve compatible child token contracts when replacing composed slots.
- Put theme, default, and state values in settings and token-derived style in `styles`. Put highly variable values
  such as text, accessibility props, handlers, sources, and refs into `usePrepareProps` slot props.

## State, hooks, and refs

- `usePrepareProps` and `useStyling` are hook phases: call them on every render and never conditionally. Hooks,
  context, controlled and uncontrolled state, and interaction hooks belong in `usePrepareProps`.
- Return `{ slotProps, state }`; `state` is the typed payload for `render`, not necessarily React state. Keep `render`
  hook-free.
- Convert `componentRef` to the native root `ref` during preparation, commonly with `useViewCommandFocus`, and type
  ref-bearing roots with `React.PropsWithRef<...>`. For imperative native APIs, use an internal native ref plus
  `useImperativeHandle`; native-core's [legacy Callout](../../../packages/agentic/native-core/src/legacy/callout/Callout.tsx)
  shows that pattern behind a legacy API.

## Platform-specific implementations

Use React Native resolution for `.android.tsx`, `.macos.tsx`, `.windows.tsx`, and `.win32.tsx`, and for platform
settings files. Keep the same public descriptor and props across variants while allowing different native slots and
preparation logic, as deprecated Button on Android and RadioButton on macOS and Win32 do. Keep imports from platform
React Native forks inside their platform files (R-REPO-002). A platform file whose root is a native component also
needs the native overlay from the [classification guide](classification.md#4-native-obligations).

## Maintenance boundaries

- Do not rewrite v0 code to `@fluentui-react-native/composition`, `@fluentui-react-native/framework`, or framework-base
  `phasedComponent`, `directComponent`, or `useSlot` patterns as part of maintenance.
- Do not apply v1 slot types, flat state tokens, `useTokens`, or the v1 `.customize({ token: value, state: {...} })`
  shape to v0 code.
- Prefer surgical fixes. Migration to v1 is a separate task and must account for documented prop, token, slot, and
  export differences such as [Button's migration guide](../../../packages/components/Button/MIGRATION.md).

## Validation

Run the owning packages' declared scripts. For the framework itself:

```bash
yarn workspace @uifabricshared/foundation-compose build
yarn workspace @uifabricshared/foundation-compose lint
yarn workspace @uifabricshared/foundation-compose test
```

For behavior changes, also build and test the consumer package, for example:

```bash
yarn workspace @fluentui-react-native/button build
yarn workspace @fluentui-react-native/button test
```

Update snapshots only after reviewing the rendered slot tree. Changes to settings override or merge semantics, or to
token processing, also require the `@uifabricshared/foundation-settings` or `@uifabricshared/foundation-tokens` tests.
Manual and end-to-end coverage for v0 components uses the [legacy test apps](legacy-test-apps.md).

## Review checklist

- Classification is supported by imports and structure, not a directory name (R-CLASSIFY-001).
- The change is maintenance, not an unrequested migration or new v0 component (R-V0-001).
- Settings layers, `_overrides`, `_precedence`, filters, and token key lists remain intact (R-V0-002).
- `componentRef`, deprecated exports, `I`-prefixed types, and display names are unchanged (R-V0-003).
- Hooks run only in `usePrepareProps` and `useStyling`; `render` stays hook-free.
- Platform variants keep the same public descriptor; fork imports stay in platform files.
- Snapshot updates were reviewed rather than accepted blindly.
